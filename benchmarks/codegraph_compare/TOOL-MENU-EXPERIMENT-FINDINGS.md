# Tool-Menu-Size Experiment: Findings

**Experiment:** Does reducing MCP tool count from 8 to 1 improve agent
task-completion and reduce tool mis-pick rate on TSA's 21-question benchmark?

**Status: STATIC ANALYSIS ONLY — live agent run has not been executed.**

The `tsa_explore` umbrella tool (Condition B) does not exist in the current
codebase.  This document records the experimental design, all 10 fairness rules,
the static pre-estimate, and the null-result honest framing required before any
product decision is made.

---

## Conditions

| Condition | Tool surface | Tool count |
|---|---|---|
| **A — full facade** | `search`, `nav`, `structure`, `health`, `edit`, `project`, `index`, `viz`, `set_project_path` | 9 |
| **B — 1-tool (hypothetical)** | `tsa_explore` (does not exist) | 1 |

The research question is whether CodeGraph's claimed "fewer tools → fewer
mis-picks" effect replicates on TSA's task set.

---

## Methodology

### Task set

21 questions drawn from `questions.yaml` (7 repos × 3 questions each).
Five categories:

| Category | Questions | Correct Condition-A tools |
|---|---|---|
| entrypoint-tracing | 7 | `nav`, `search` |
| call-chain | 4 | `nav` |
| module-boundary | 4 | `structure` |
| change-impact | 3 | `nav`, `search` |
| subsystem-overview | 3 | `structure`, `health` |

### All 10 fairness rules (applied identically to both conditions)

These rules are enforced by the main harness.  They apply without modification
to the tool-menu experiment.  Violating any rule invalidates the run.

1. **Pinned commits** — all repos use a fixed SHA from `repos.yaml`; no HEAD-tracking.
2. **Same model for all conditions** — the selected model ID is applied uniformly.
3. **Identical question text** — each condition receives the exact same prompt string.
4. **Minimum 4 repeats** — the summary drops any condition with fewer than 4 repeats.
5. **Report median, not best** — `overall`, `elapsed_seconds`, `total_tokens` are
   summarized as median across repeats.
6. **Cold and warm reported separately** — arms with `index_mode: cold` are never
   averaged with `index_mode: warm`.
7. **Index build time excluded from warm query time** — `elapsed_seconds` in a warm
   run begins after the index is confirmed ready.
8. **Flag low-quality answers** — any run with `EvalRecord.overall < 2.5` is marked
   `LOW_QUALITY` even if token-efficient.
9. **Auto-penalize phantom citations** — citations to files absent from the pinned
   repo reduce `citation_quality` before human/LLM review.
10. **No silent drops** — timeouts and exceptions are recorded as `RunRecord` entries
    with `error` set; they appear as `FAILED`, not omitted.

**Fairness-rule audit (design-time):** All 10 rules are applied identically to
both conditions by design.  See `tool_menu_experiment.py`::`verify_fairness_rules_applied`.

### Measurement targets (per condition per repeat)

- **Agent task-completion rate:** fraction of runs where `EvalRecord.overall >= 3.5`.
- **Tool mis-pick rate:** fraction of tool calls where the agent selected a tool
  that did not match the category's correct-tool mapping.
- **Token consumption:** `RunRecord.total_tokens` (median across repeats).

### Static pre-estimate (NOT a measurement)

Generated by `tool_menu_experiment.py`::`static_analysis_estimate`.
Raw output in `results/tool_menu_experiment_static_estimate.json`.

| Metric | Condition A (8 tools) | Condition B (1 tool) |
|---|---|---|
| Tool count | 9 | 1 |
| Theoretical random mis-pick rate | 82.2% | 0.0% |
| Estimated task-completion rate | 85% | 82% |
| Estimated tool mis-pick rate | 18% | 0% |
| Estimated token ratio | 1.0x | ~0.95x |
| Confidence | low | low |

**Important caveat on the theoretical random rate:** 82.2% is the rate for a
purely random tool-picker on the 21-question task set.  Real agents are not
random; they read tool descriptions.  The actual mis-pick rate for a
well-prompted Condition-A agent is likely much lower and can only be measured
with a live run.

**Important caveat on Condition B completion rate:** The 82% estimate assumes
`tsa_explore`'s internal routing is at least as good as explicit tool selection.
If routing introduces ambiguity or hides tool semantics from the agent, completion
rate could fall below 82%.  This is precisely the unknown the live experiment
is designed to resolve.

## Was the CodeGraph effect observed?

**Not determined — static analysis only.**

CodeGraph's README claims: "fewer exposed tools → fewer agent mis-picks."
On TSA's current 8-tool surface, the theoretical random mis-pick rate is high
(82%), but real agents with good system prompts are not random pickers.
Whether a 1-tool surface produces measurably fewer mis-picks on TSA's specific
task set is an empirical question that requires a live agent run.

**Honest null-result language:** This experiment cannot confirm or deny the
CodeGraph effect.  The static analysis establishes a plausible prior — the
1-tool surface *should* eliminate the random-baseline mis-pick rate entirely —
but whether that translates to better real-agent outcomes is unknown.

## Next steps (required for a real result)

1. **Implement `tsa_explore`** — the Case B Phase 2 engineering task (currently
   out of scope; see `rfcs/ROADMAP-beyond-codegraph.md` and plan.md Phase 1b notes).
2. **Add `adapters/tsa_1tool.py`** — following the interface in
   `adapters/tree_sitter_analyzer.py`.
3. **Register Condition B arm** in `arms.yaml`:

   ```yaml
   - id: tsa-1tool-warm
     adapter: tsa_1tool
     index_mode: warm
   ```

4. **Run the pilot phase**:

   ```bash
   uv run python benchmarks/codegraph_compare/run.py phase pilot \
       --arms tsa-warm,tsa-1tool-warm \
       --agent-backend claude \
       --repeats 4
   ```

5. **Evaluate and analyze**:

   ```bash
   uv run python benchmarks/codegraph_compare/evaluate.py \
       --runs results/runs.jsonl --out results/evals.jsonl

   uv run python benchmarks/codegraph_compare/analyze.py \
       --runs results/runs.jsonl --evals results/evals.jsonl \
       --arms tsa-warm,tsa-1tool-warm
   ```

6. **Update this document** with real RunRecord results, replacing the static
   pre-estimate table with measured values.

## Decision rule for product action

Per `rfcs/ROADMAP-beyond-codegraph.md` and the Phase 1b scope boundary:

> Phase 1b findings must be reviewed by a human and judged "effect confirmed"
> before any Case B Phase 2 engineering (tsa_explore routing layer,
> env-var visibility switch) is started.

A static pre-estimate alone is **not** sufficient to trigger product action.
A live pilot run showing a statistically meaningful improvement in
task-completion rate and/or mis-pick rate is required.
